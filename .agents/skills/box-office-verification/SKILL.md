# 박스오피스 데이터 검증

KOBIS 박스오피스 데이터를 파싱·저장·집계하는 변경이 PRD, ARCHITECTURE, ERD의 계약과 일치하는지 확인한다. 이 Skill은 API 응답 파싱, DB 저장, 캐시, 목록 결과, 순위·매출·관객 지표의 정확성이 바뀌는 작업에 호출한다.

다음 작업에는 호출하지 않는다.

- 문구, 번역, 색상, 여백, 폰트, 아이콘처럼 데이터 흐름과 결과값을 바꾸지 않는 수정
- 데이터 요청·파싱·저장·집계와 무관한 화면 레이아웃 변경
- 문서 서식만 바꾸는 수정

## ① 입력과 기준 찾기

1. 변경 전후의 입력 경로를 확인한다. KOBIS 원본 응답, 내부 API 요청·응답, DB 스키마, 캐시 키·TTL, 인사이트 집계 중 무엇이 영향을 받는지 명시한다.
2. `PRD.md`에서 화면에 보여야 할 값과 상태별 안내를 확인하고, `ARCHITECTURE.md`에서 KOBIS 엔드포인트·정규화·캐시 정책을 확인하며, `ERD.md`에서 테이블 관계·제약·JOIN 기준을 확인한다.
3. 다음 데이터 계약을 기준으로 검증 대상을 정한다.
   - 영화: `movieCd`, `movieNm`, `openDt`
   - 기간: `periodType` (`daily` / `weekly` / `weekend`), `targetDate`
   - 실적: `rank`, `salesAmt`, `audiCnt`, `salesAcc`, `audiAcc`
4. KOBIS의 숫자 값은 문자열일 수 있다. 정수 파싱 후 유한값인지, 음수가 아닌지, 필수 값이 누락되지 않았는지 확인한다. 파싱 실패 레코드를 0으로 바꿔 조용히 저장하지 않는다.
5. `KOBIS_API_KEY`, `SUPABASE_SECRET_KEY`의 실제 값은 읽거나 출력하거나 테스트 fixture에 넣지 않는다. 서버 환경 변수 이름만 사용한다.

## ② 변경에 맞춘 검사 선택

변경 범위에 맞는 검사를 선택하고, 실행하지 않은 검사는 보고에서 `미실행`으로 남긴다.

| 변경 유형 | 반드시 확인할 검사 |
| --- | --- |
| KOBIS 응답 파싱 | 문자열 숫자의 정상 변환, 빈 문자열·비숫자·음수·필수 필드 누락 처리, `openDt`의 유효한 날짜 변환 또는 `null` 처리 |
| 목록 API | 날짜·기간 유형 검증, 일간·주간·주말별 올바른 KOBIS 요청 구성, 순위 숫자 정렬, 필수 출력 필드 |
| DB 저장 또는 스키마 | `movie_code`의 중복 방지, `(period_type, target_date)`의 유일성, `(period_id, movie_id)`와 `(period_id, rank)` 제약, 영화·기간·실적 JOIN 결과 |
| 캐시 | 유효 캐시 hit 시 외부 호출 생략, miss/만료 시 갱신, 정상 빈 배열 캐시, 외부 API 실패 시 오래된 정상 캐시의 `stale: true` 반환 |
| 인사이트 지표 | 선택한 7·14·30일 범위만 집계하는지, `sales_amt`·`audi_cnt` 합계, Top 5/10의 숫자 기준 정렬, 중복 기간이 합계에 포함되지 않는지 |
| 상태 처리 | 정상 빈 응답, API 오류, 검색 결과 없음을 서로 다른 상태와 안내 문구로 반환·표시하는지 |

가능하면 작은 고정 fixture를 사용해 예상값을 계산한다. 최소한 영화 2개와 날짜 3개로 순위 변화, 합계, 누적값을 확인한다. DB가 필요한 검사는 운영 DB가 아닌 로컬·테스트 환경에서 실행한다.

## ③ 결과와 중단 기준

검사 결과는 다음 세 상태를 섞지 않고 항목별로 보고한다.

| 상태 | 의미 | 보고 방식 |
| --- | --- | --- |
| 통과 | 검사를 실행했고, 기대값·제약·상태 처리가 모두 일치했다. | 검사명, 사용한 입력 또는 fixture, 확인한 결과를 짧게 쓴다. |
| 실패 | 검사를 실행했고, 기대값과 실제 결과가 달랐거나 오류가 발생했다. | 재현 조건, 기대값, 실제값, 영향 범위를 쓰고 수정 전에는 완료로 보고하지 않는다. |
| 미실행 | 검사가 필요하지만 환경·스크립트·자격 증명·시간 등의 이유로 실행하지 못했다. | 실행하지 못한 이유와 다음에 필요한 조건을 쓴다. 미실행을 통과로 표현하지 않는다. |

다음 중 하나에 해당하면 작업을 중단하고 실패 또는 미실행으로 보고한다.

- 실제 비밀 키가 필요하지만 안전한 서버 측 테스트 환경이 없다.
- 숫자 변환·DB 제약·집계 기준 중 하나의 기대 동작이 문서와 충돌하거나 확정되지 않았다.
- 정상 빈 응답, API 오류, 검색 결과 없음 중 둘 이상이 같은 상태로 처리된다.
- 캐시 갱신이 유효한 캐시를 덮어쓰거나, 외부 API 실패 시 마지막 정상 캐시를 손상시킬 가능성이 있다.

최종 보고는 `통과`, `실패`, `미실행` 세 구역으로 나눈다. 변경 파일과 실행 명령을 함께 쓰되, 로그·보고·첨부물에 비밀 값을 포함하지 않는다.
